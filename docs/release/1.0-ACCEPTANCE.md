# Syzygy 1.0 Release Acceptance

Status: preparation branch only. This document is a release gate, not authorization to merge or publish.

## Release principles

- APD is observe-only for 1.0. It may classify bottlenecks and emit evidence-backed recommendations, but it must not alter bitrate, resolution, frame rate, codec, FEC, capture mode, encoder settings, or sender pacing.
- Existing WAN pacing and FEC remain the only transport control path.
- No silent dropping or eviction of reference-dependent encoded frames.
- Session teardown must wait for queued and in-flight owners; stale generations must not publish into a reconnected session.
- Every reported metric must have a documented source, unit, timing boundary, freshness rule, and known limitation.
- A successful CI build is necessary but not sufficient for release.

## Release blockers

### A. Runtime per-session video path

- [ ] Replace the shared `mail::video_packets` queue with the bounded per-session scheduler in the live encoder/broadcaster path.
- [ ] Register and unregister sessions using stable IDs and generation tokens.
- [ ] Route each encoded frame to its owning session; reject stale generations.
- [ ] Translate queue overflow/recovery outcomes into the existing per-session IDR request path.
- [ ] Preserve FIFO order, frame indices, RTP sequence numbers, FEC block numbering, and GCM IV uniqueness/ordering.
- [ ] Prove one stalled client cannot starve or erase another client's frames.
- [ ] Add deterministic multi-session tests for overload, keyframe recovery, mixed frame sizes, and reconnect.
- [ ] Verify teardown while frames are queued and while packetization/send is in flight.

### B. Packetizer and paced sender separation

- [ ] Introduce a bounded complete-FEC-block handoff with explicit byte and frame limits.
- [ ] Keep all packet sequence allocation and encryption state serialized per session.
- [ ] Move pacing waits off the packetizer/encoder worker without changing the existing pacing algorithm.
- [ ] Add fair per-session sender service; do not let one session monopolize the socket worker.
- [ ] Define and test queue-full behavior without silently discarding dependent frames.
- [ ] Capture platform-specific send return values and partial-batch outcomes where the API exposes them.
- [ ] Distinguish local socket backpressure, MTU errors, route/peer failures, and unknown errors; never train network congestion from local errors alone.
- [ ] Add shutdown, cancellation, and worker-failure tests for every handoff boundary.

### C. Pipeline accounting and telemetry

- [x] Capture callback timing where the backend provides a verified boundary.
- [x] Capture-to-encoder-consumption age.
- [x] Safe FFmpeg PTS correlation for delayed/reordered output.
- [x] Encoder submission-to-output availability timing.
- [x] Packetization, FEC encode, encryption, pacing wait, socket submission-call and dequeue-to-first-submission timing.
- [ ] Encoder in-flight count and oldest in-flight age.
- [ ] GPU/encoder completion fence integration where supported; queue dequeue is not completion.
- [ ] Per-session encoded-frame queue depth, bytes, and oldest age.
- [ ] Prepared-FEC-block queue depth, bytes, and oldest age.
- [ ] Dropped/replaced frame counters by reason, frame type, and recovery action.
- [ ] Confirm independent freshness timestamps for host, sender, network, loss, jitter, and client feedback.
- [ ] Ensure unavailable/stale measurements remain unavailable and do not produce false bottleneck classifications.

### D. Network and client feedback

- [x] ENet RTT and variance freshness tied to new acknowledged-packet samples.
- [x] Client feedback receiver with validation and wrap-safe frame index checks.
- [x] FEC recovery loss denominator validation.
- [ ] Validate RTT/variance and media jitter against real packet captures on LAN and WAN.
- [ ] Validate packet-loss estimates against controlled loss and FEC recovery tests.
- [ ] Verify the optional client feedback extension with a compatible test sender/client.
- [ ] Confirm ordinary Moonlight clients report unavailable client decode/presentation feedback rather than fabricated values.

The client feedback sender is intentionally not implemented here: this repository is the Syzygy host. A compatible client is a separate deliverable and must not be silently added outside this repository boundary.

### E. Physical T1600 acceptance

- [ ] Run the documented acceptance matrix on the physical Precision T1600 / GTX 1060 6 GB.
- [ ] Record driver, kernel, GPU, encoder, codec, resolution, frame rate, packet size, FEC, and client details.
- [ ] Validate H.264 NVENC and HEVC NVENC at 1080p60.
- [ ] Validate headless capture and audio/input behavior on the target KDE/Wayland environment.
- [ ] Run sustained streaming and multi-client isolation tests.
- [ ] Capture the APD telemetry report and compare baseline versus candidate pipeline.
- [ ] Verify no regression in frame continuity, latency, CPU/GPU utilization, or recovery behavior.

### F. General release quality

- [ ] Reconcile and integrate the headless audio/touch work and fractional-scaling touch work into the release candidate.
- [ ] Run all Linux CI, unit, smoke, package, RPM startup, and static checks on the final release candidate commit.
- [ ] Review all outstanding TODOs, compiler warnings, known limitations, and user-facing version strings.
- [ ] Verify clean install, upgrade, configuration migration, and uninstall behavior.
- [ ] Produce release notes, known-issues list, checksums, and reproducible build provenance.
- [ ] Confirm version metadata and package naming are consistently 1.0.0.
- [ ] Obtain explicit owner approval before merging, tagging, or publishing.

## Definition of done

Syzygy 1.0 is release-ready only when every release blocker above is either completed and evidenced or explicitly approved as a documented 1.0 limitation. Physical T1600 acceptance is mandatory for the advertised GTX 1060 support. CI success alone cannot close that gate.

No merge, release tag, or publication is authorized by this checklist.
